## 1. 계정 관리 시나리오

### SC-A01 회원가입 및 이메일 중복 확인

**관련 UC**: UC-A01, UC-A02
**액터**: 비회원 (신규 사용자)
**사전 조건**: 사용자가 회원가입 페이지에 접근한 상태이다.
**사후 조건**: 계정이 생성되고, 기본 카테고리 6종(업무, 개인, 학습, 회의, 프로젝트, 긴급 업무)이 자동으로 생성된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 이메일 입력 필드에 이메일 주소를 입력한다.
2. 사용자가 중복 확인 버튼을 클릭하거나 다음 필드로 포커스를 이동한다.
3. 시스템이 해당 이메일이 이미 등록된 계정에 사용 중인지 확인한다.
4. 시스템이 "사용 가능한 이메일입니다"를 표시한다.
5. 사용자가 비밀번호를 입력한다 (최소 8자, 영문자·숫자·특수문자 각 1자 이상).
6. 사용자가 비밀번호 확인을 입력한다.
7. 사용자가 회원가입 버튼을 클릭한다.
8. 시스템이 입력값(이메일 형식, 비밀번호 정책)을 검증한다.
9. 시스템이 계정을 생성하고 기본 카테고리 6종을 자동 생성한다.
10. 시스템이 로그인 페이지로 리디렉션하며 "회원가입이 완료되었습니다" 메시지를 표시한다.

#### 대안 흐름 (Alternative Flow)

- A1. [비밀번호와 비밀번호 확인이 일치하지 않는 경우]: 시스템이 "비밀번호가 일치하지 않습니다" 메시지를 표시하고, 사용자가 다시 입력하도록 유도한다.

#### 예외 흐름 (Exception Flow)

- E1. [이미 등록된 이메일인 경우]: 시스템이 "이미 사용 중인 이메일입니다" 메시지를 표시하고 (409 Conflict), 사용자가 다른 이메일을 입력하도록 유도한다.
- E2. [비밀번호 정책 미충족]: 시스템이 "비밀번호는 최소 8자이며, 영문자·숫자·특수문자를 각 1자 이상 포함해야 합니다" 메시지를 표시한다 (400 Bad Request).
- E3. [이메일 형식 오류]: 시스템이 "올바른 이메일 형식을 입력해 주세요" 메시지를 표시한다 (400 Bad Request).

### SC-A02 로그인

**관련 UC**: UC-A03
**액터**: 가입된 사용자
**사전 조건**: 사용자가 로그인 페이지에 접근한 상태이다.
**사후 조건**: 액세스 토큰(유효 기간 1시간)과 리프레시 토큰(유효 기간 7일)이 발급되고, 사용자가 대시보드로 이동한다.

#### 기본 흐름 (Main Flow)

1. 사용자가 이메일 주소를 입력한다.
2. 사용자가 비밀번호를 입력한다.
3. 사용자가 로그인 버튼을 클릭한다.
4. 시스템이 이메일과 비밀번호의 일치 여부를 검증한다.
5. 시스템이 액세스 토큰(1시간)과 리프레시 토큰(7일)을 발급한다.
6. 시스템이 사용자를 대시보드 페이지로 이동시킨다.

#### 대안 흐름 (Alternative Flow)

- A1. [액세스 토큰 만료 후 API 요청]: 시스템이 401을 반환하면 클라이언트가 PostgreSQL에 저장된 유효한 리프레시 토큰을 기준으로 새 액세스 토큰을 자동 갱신한다.
- A2. [리프레시 토큰도 만료된 경우]: 시스템이 401을 반환하고, 사용자를 로그인 페이지로 이동시키며 "세션이 만료되었습니다. 다시 로그인해 주세요" 메시지를 표시한다.

#### 예외 흐름 (Exception Flow)

- E1. [이메일 또는 비밀번호 불일치]: 시스템이 "이메일 또는 비밀번호가 올바르지 않습니다" 메시지를 표시한다 (401 Unauthorized). 구체적인 오류 원인은 보안상 노출하지 않는다.
- E2. [존재하지 않는 이메일]: E1과 동일한 메시지를 표시한다 (보안상 이메일 존재 여부 미노출).

### SC-A03 로그아웃

**관련 UC**: UC-A04
**액터**: 인증된 사용자
**사전 조건**: 사용자가 로그인 상태이다.
**사후 조건**: 발급된 토큰이 무효화되고, 사용자가 로그인 페이지로 이동한다.

#### 기본 흐름 (Main Flow)

1. 사용자가 내비게이션에서 로그아웃 버튼을 클릭한다.
2. 시스템이 PostgreSQL에 저장된 현재 세션의 리프레시 토큰을 무효화한다.
3. 시스템이 클라이언트 측에 저장된 액세스 토큰 정보를 삭제한다.
4. 시스템이 사용자를 로그인 페이지로 이동시킨다.

#### 예외 흐름 (Exception Flow)

- E1. [이미 만료된 토큰으로 로그아웃 요청]: 시스템이 이미 만료된 세션으로 처리하고 로그인 페이지로 이동시킨다.

### SC-A04 내 정보 조회 및 수정

**관련 UC**: UC-A05, UC-A06
**액터**: 인증된 사용자
**사전 조건**: 사용자가 로그인 상태이며, 내 정보 페이지에 접근한 상태이다.
**사후 조건**: 변경된 정보(이름 등)가 저장되고 화면에 반영된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 내 정보 페이지로 이동한다.
2. 시스템이 현재 사용자의 이메일, 이름 등 프로필 정보를 조회하여 표시한다.
3. 사용자가 수정할 항목(예: 이름)을 변경한다.
4. 사용자가 저장 버튼을 클릭한다.
5. 시스템이 입력값을 검증한다.
6. 시스템이 변경 내용을 저장하고 "정보가 수정되었습니다" 메시지를 표시한다.
7. 화면에 갱신된 정보가 표시된다.

#### 예외 흐름 (Exception Flow)

- E1. [인증 토큰 없이 접근]: 시스템이 401을 반환하고 로그인 페이지로 이동시킨다.
- E2. [유효하지 않은 입력값]: 시스템이 400 Bad Request를 반환하고 오류 메시지를 표시한다.

### SC-A05 비밀번호 재설정

**관련 UC**: UC-A07, UC-A08
**액터**: 비밀번호를 분실한 사용자
**사전 조건**: 사용자가 비밀번호 재설정 요청 페이지에 접근한 상태이다.
**사후 조건**: 새로운 비밀번호로 계정이 업데이트된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 가입된 이메일 주소를 입력하고 재설정 링크 요청 버튼을 클릭한다.
2. 시스템이 해당 이메일로 등록된 계정을 확인한다.
3. 시스템이 유효 기간 30분의 비밀번호 재설정 링크를 생성하여 해당 이메일로 발송한다.
4. 시스템이 "입력하신 이메일로 재설정 링크를 발송했습니다" 메시지를 표시한다.
5. 사용자가 이메일의 링크를 클릭하여 비밀번호 재설정 페이지로 접근한다.
6. 시스템이 링크의 유효성(만료 여부, 토큰 정합성)을 검증한다.
7. 사용자가 새 비밀번호를 입력하고 비밀번호 확인을 입력한다.
8. 사용자가 변경 버튼을 클릭한다.
9. 시스템이 비밀번호 정책을 검증한다 (최소 8자, 영문자·숫자·특수문자 각 1자 이상).
10. 시스템이 새 비밀번호를 bcrypt로 해싱하여 저장한다.
11. 시스템이 "비밀번호가 변경되었습니다. 새 비밀번호로 로그인해 주세요" 메시지를 표시하고 로그인 페이지로 이동시킨다.

#### 대안 흐름 (Alternative Flow)

- A1. [등록되지 않은 이메일 입력]: 보안상 이메일 존재 여부를 노출하지 않고 "입력하신 이메일로 재설정 링크를 발송했습니다"와 동일한 안내 메시지를 표시한다.

#### 예외 흐름 (Exception Flow)

- E1. [30분 유효기간 만료된 링크 접근]: 시스템이 "재설정 링크가 만료되었습니다. 다시 요청해 주세요" 메시지를 표시하고 재발송 버튼을 제공한다.
- E2. [이미 사용된 링크 접근]: 시스템이 "이미 사용된 링크입니다. 다시 요청해 주세요" 메시지를 표시한다.
- E3. [새 비밀번호 정책 미충족]: 시스템이 "비밀번호는 최소 8자이며, 영문자·숫자·특수문자를 각 1자 이상 포함해야 합니다" 메시지를 표시한다 (400 Bad Request).

### SC-A06 회원 탈퇴

**관련 UC**: UC-A09
**액터**: 인증된 사용자
**사전 조건**: 사용자가 로그인 상태이며, 내 정보 페이지에 접근한 상태이다.
**사후 조건**: 사용자 데이터가 즉시 하드 삭제되고, 세션이 종료된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 내 정보 페이지에서 회원 탈퇴 버튼을 클릭한다.
2. 시스템이 확인 모달을 표시한다 ("탈퇴 시 모든 데이터가 즉시 삭제되며 복구할 수 없습니다. 정말 탈퇴하시겠습니까?").
3. 사용자가 현재 비밀번호를 입력하여 본인 확인을 수행한다.
4. 사용자가 탈퇴 확인 버튼을 클릭한다.
5. 시스템이 비밀번호를 검증한다.
6. 시스템이 사용자 데이터를 즉시 하드 삭제한다 (소프트 삭제 아님).
7. 시스템이 현재 세션을 종료하고 로그인 페이지로 이동시킨다.

#### 대안 흐름 (Alternative Flow)

- A1. [사용자가 탈퇴 확인 모달에서 취소 클릭]: 모달이 닫히고 내 정보 페이지 상태를 유지한다.

#### 예외 흐름 (Exception Flow)

- E1. [비밀번호 불일치]: 시스템이 "비밀번호가 올바르지 않습니다" 메시지를 표시한다 (401).
- E2. [팀의 유일한 ADMIN인 경우]: 시스템이 "팀 [팀명]의 유일한 관리자입니다. 탈퇴 전 다른 멤버에게 관리자 권한을 양도하거나 팀을 삭제해 주세요" 메시지를 표시한다 (422 Unprocessable Entity, TEAM-002).

## 2. 할일 관리 시나리오

### SC-T01 할일 생성

**관련 UC**: UC-T01
**액터**: 인증된 사용자 (개인 할일), 팀 ADMIN 또는 MEMBER (팀 할일)
**사전 조건**: 사용자가 로그인 상태이며, 할일 생성 화면에 접근한 상태이다.
**사후 조건**: 새 할일이 저장되고, 할일 목록에 표시된다. 진행 상태는 기본값 PLANNED로 설정된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 할일 생성 버튼을 클릭한다.
2. 시스템이 할일 생성 폼을 표시한다.
3. 사용자가 제목을 입력한다 (필수).
4. 사용자가 선택 항목(설명, 시작일, 종료일(마감일), 카테고리, 진행 상태)을 입력한다.
5. 사용자가 저장 버튼을 클릭한다.
6. 시스템이 입력값을 검증한다 (제목 필수, 종료일 >= 시작일, 진행 상태 enum 유효성).
7. 시스템이 할일을 저장한다 (개인 할일: user_id 설정, team_id = NULL).
8. 시스템이 "할일이 생성되었습니다" 메시지를 표시하고 할일 목록으로 이동한다.

#### 대안 흐름 (Alternative Flow)

- A1. [팀 할일 생성]: 사용자가 팀을 선택하면 team_id가 설정되고 user_id는 생성자 참조로 저장된다. 해당 팀의 ADMIN 또는 MEMBER 역할이 있어야 한다.
- A2. [진행 상태를 별도로 선택하지 않은 경우]: 시스템이 기본값 PLANNED를 자동 적용한다.

#### 예외 흐름 (Exception Flow)

- E1. [제목 미입력]: 시스템이 "제목은 필수 항목입니다" 메시지를 표시한다 (400 Bad Request, TODO-001).
- E2. [종료일이 시작일보다 이른 경우]: 시스템이 "종료일은 시작일 이후여야 합니다" 메시지를 표시한다 (400 Bad Request, TODO-002).
- E3. [유효하지 않은 진행 상태 값]: 시스템이 "유효하지 않은 진행 상태입니다" 메시지를 표시한다 (400 Bad Request, TODO-003).
- E4. [팀 할일 생성 시 VIEWER 역할]: 시스템이 "팀 할일 생성 권한이 없습니다" 메시지를 표시한다 (403 Forbidden, AUTH-004).

### SC-T02 할일 수정

**관련 UC**: UC-T02
**액터**: 할일 소유자 (개인 할일), 팀 ADMIN 또는 MEMBER (팀 할일)
**사전 조건**: 사용자가 로그인 상태이며, 수정 대상 할일이 존재한다.
**사후 조건**: 변경된 할일 정보가 저장된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 할일 목록에서 수정할 항목을 선택한다.
2. 시스템이 할일 상세/편집 화면을 표시한다.
3. 사용자가 제목, 설명, 시작일, 종료일, 카테고리, 진행 상태 중 원하는 항목을 수정한다.
4. 사용자가 저장 버튼을 클릭한다.
5. 시스템이 수정 권한을 확인한다 (개인 할일: 소유자 여부, 팀 할일: ADMIN 또는 MEMBER 여부).

7. 시스템이 변경 내용을 저장하고 "할일이 수정되었습니다" 메시지를 표시한다.

#### 예외 흐름 (Exception Flow)

- E4. [종료일이 시작일보다 이른 경우]: 시스템이 "종료일은 시작일 이후여야 합니다" 메시지를 표시한다 (400 Bad Request, TODO-002).

**관련 UC**: UC-C01

1. 사용자가 카테고리 생성 버튼을 클릭한다.
2. 시스템이 카테고리 생성 폼을 표시한다 (카테고리명, 색상 태그 입력).

- E2. [팀 카테고리 생성 시 ADMIN이 아닌 경우]: 시스템이 403 Forbidden을 반환한다.
- E3. [색상 코드 형식 오류]: 시스템이 "올바른 HEX 색상 코드를 입력해 주세요 (#RRGGBB 형식)" 메시지를 표시한다 (400 Bad Request, CAT-004).

#### 예외 흐름 (Exception Flow)

- E1. [팀 이름 미입력]: 시스템이 "팀 이름은 필수 항목입니다" 메시지를 표시한다 (400 Bad Request).

### SC-M02 팀 멤버 초대

**관련 UC**: UC-M02
**액터**: 팀 ADMIN
**사전 조건**: 사용자가 팀 ADMIN 역할이며, 초대 대상 사용자가 시스템에 등록되어 있다.
**사후 조건**: TeamInvitation이 PENDING 상태로 생성되고, 피초대자에게 TEAM_INVITE 인앱 알림이 발송된다.

#### 기본 흐름 (Main Flow)

1. 팀 ADMIN이 팀 관리 페이지에서 멤버 초대 버튼을 클릭한다.
2. 시스템이 초대 폼(이메일 입력, 역할 선택)을 표시한다.
3. ADMIN이 초대할 사용자의 이메일을 입력하고, 역할(MEMBER 또는 VIEWER)을 선택한다.
4. ADMIN이 초대 버튼을 클릭한다.
5. 시스템이 초대 대상 사용자가 시스템에 등록되어 있는지 확인한다.
6. 시스템이 해당 사용자가 이미 팀 소속인지, 또는 PENDING 초대가 있는지 확인한다.
7. 시스템이 TeamInvitation(status=PENDING, expires_at=설정값)을 생성한다.
8. 시스템이 피초대자에게 TEAM_INVITE 인앱 알림을 발송한다.
9. 시스템이 "초대를 발송했습니다" 메시지를 표시한다.

#### 예외 흐름 (Exception Flow)

- E1. [ADMIN 역할이 아닌 사용자가 초대 시도]: 시스템이 403 Forbidden을 반환한다 (AUTH-005).
- E2. [이미 팀에 소속된 사용자 초대 시도]: 시스템이 "이미 팀에 소속된 사용자입니다" 메시지를 표시한다 (409 Conflict, INV-002).
- E3. [PENDING 초대가 이미 있는 사용자 초대 시도]: 시스템이 "해당 사용자에게 이미 대기 중인 초대가 있습니다" 메시지를 표시한다 (409 Conflict, INV-002).
- E4. [시스템에 등록되지 않은 이메일 초대 시도]: 시스템이 "등록되지 않은 사용자입니다" 메시지를 표시한다 (404 Not Found).
- E5. [ADMIN 역할로 초대 시도]: 시스템이 "초대 가능한 역할은 MEMBER 또는 VIEWER입니다" 메시지를 표시한다 (400 Bad Request, INV-001).

### SC-M03 팀 초대 수락 및 거절

**관련 UC**: UC-M09, UC-M10
**액터**: 팀 초대를 받은 사용자 (피초대자)
**사전 조건**: 사용자가 로그인 상태이며, 유효한 PENDING 초대가 존재한다.
**사후 조건 (수락)**: TeamInvitation.status=ACCEPTED, TeamMember가 생성되며 관련 알림이 읽음 처리된다.
**사후 조건 (거절)**: TeamInvitation.status=DECLINED, 팀에 가입되지 않는다.

#### 기본 흐름 (수락, Main Flow)

1. 피초대자가 인앱 알림 목록에서 팀 초대 알림을 확인한다.
2. 피초대자가 초대 수락 버튼을 클릭한다.
3. 시스템이 초대의 유효성(PENDING 상태, 만료 여부)을 확인한다.
4. 시스템이 피초대자가 이미 팀 소속이 아닌지 확인한다.
5. 시스템이 TeamInvitation.status를 ACCEPTED로 변경한다.
6. 시스템이 초대의 role 값으로 TeamMember를 생성한다.
7. 시스템이 관련 TEAM_INVITE 알림을 읽음 처리한다.
8. 시스템이 "팀에 가입되었습니다" 메시지를 표시하고 팀 할일 목록 페이지로 이동한다.

#### 기본 흐름 (거절, Main Flow)

1. 피초대자가 인앱 알림 목록에서 팀 초대 알림을 확인한다.
2. 피초대자가 초대 거절 버튼을 클릭한다.
3. 시스템이 TeamInvitation.status를 DECLINED로 변경한다.
4. 시스템이 "초대를 거절했습니다" 메시지를 표시한다.

#### 대안 흐름 (Alternative Flow)

- A1. [거절 후 동일 팀에서 재초대 받은 경우]: 이전 초대가 DECLINED 상태이므로 PENDING 초대 중복 없이 새 초대 생성이 가능하다.

#### 예외 흐름 (Exception Flow)

- E1. [만료된 초대 수락 시도]: 시스템이 초대 status를 EXPIRED로 변경하고 "초대가 만료되었습니다. 팀 관리자에게 재초대를 요청하세요" 메시지를 표시한다 (422, INV-005).
- E2. [이미 팀 소속인 사용자가 수락 시도]: 시스템이 "이미 팀에 소속되어 있습니다" 메시지를 표시한다 (409 Conflict, TEAM-003).

### SC-M04 팀 멤버 역할 변경

**관련 UC**: UC-M03
**액터**: 팀 ADMIN
**사전 조건**: 사용자가 팀 ADMIN 역할이며, 역할 변경 대상 멤버가 팀에 소속되어 있다.
**사후 조건**: 대상 멤버의 역할이 변경된다.

#### 기본 흐름 (Main Flow)

2. 시스템이 변경 가능한 역할 목록(ADMIN, MEMBER, VIEWER)을 표시한다.

4. 시스템이 변경 권한 및 최소 ADMIN 유지 조건을 확인한다.
5. 시스템이 역할을 변경하고 "역할이 변경되었습니다" 메시지를 표시한다.

### SC-M06 팀 탈퇴

**관련 UC**: UC-M05
**액터**: 팀 소속 멤버
**사전 조건**: 사용자가 로그인 상태이며, 탈퇴할 팀에 소속되어 있다.
**사후 조건**: 사용자가 팀에서 제거되고, 해당 사용자가 생성한 팀 할일의 소유권이 팀으로 귀속된다 (user_id = NULL).

#### 기본 흐름 (Main Flow)

2. 시스템이 확인 모달을 표시한다 ("탈퇴 시 해당 팀에서 생성한 할일의 소유권이 팀으로 귀속됩니다. 계속하시겠습니까?").
3. 사용자가 탈퇴 확인 버튼을 클릭한다.
4. 시스템이 최소 ADMIN 유지 조건을 확인한다.
5. 시스템이 사용자를 팀에서 제거한다.
6. 시스템이 해당 사용자가 생성한 팀 할일의 user_id를 NULL로 처리한다.
7. 시스템이 "팀에서 탈퇴했습니다" 메시지를 표시하고 팀 목록 페이지로 이동한다.

#### 대안 흐름 (Alternative Flow)

- A1. [사용자가 탈퇴 확인 모달에서 취소 클릭]: 모달이 닫히고 기존 화면 상태를 유지한다.

#### 예외 흐름 (Exception Flow)

- E1. [팀의 마지막 ADMIN이 탈퇴 시도]: 시스템이 "팀의 유일한 관리자입니다. 다른 멤버에게 관리자 권한을 양도하거나 팀을 삭제해 주세요" 메시지를 표시한다 (422, TEAM-002).

### SC-M08 팀 정보 수정 및 팀 삭제

**관련 UC**: UC-M07, UC-M08
**액터**: 팀 ADMIN
**사전 조건**: 사용자가 팀 ADMIN 역할이며, 수정 또는 삭제 대상 팀이 존재한다.
**사후 조건 (수정)**: 변경된 팀 정보가 저장된다.
**사후 조건 (삭제)**: 팀과 팀의 모든 할일·카테고리가 즉시 삭제된다. 멤버의 개인 할일은 영향받지 않는다.

#### 기본 흐름 (팀 정보 수정, Main Flow)

1. 팀 ADMIN이 팀 관리 페이지에서 팀 정보 수정 버튼을 클릭한다.
2. 시스템이 현재 팀 정보가 채워진 수정 폼을 표시한다.
3. ADMIN이 팀 이름, 설명 등을 수정한다.
4. ADMIN이 저장 버튼을 클릭한다.
5. 시스템이 변경 내용을 저장하고 "팀 정보가 수정되었습니다" 메시지를 표시한다.

#### 기본 흐름 (팀 삭제, Main Flow)

1. 팀 ADMIN이 팀 관리 페이지에서 팀 삭제 버튼을 클릭한다.
2. 시스템이 확인 모달을 표시한다 ("팀을 삭제하면 팀의 모든 할일과 카테고리가 즉시 삭제되며 복구할 수 없습니다. 정말 삭제하시겠습니까?").
3. ADMIN이 삭제 확인 버튼을 클릭한다.
4. 시스템이 팀 및 팀에 속한 모든 할일·카테고리를 즉시 삭제한다.
5. 시스템이 "팀이 삭제되었습니다" 메시지를 표시하고 팀 목록 페이지로 이동한다.

#### 예외 흐름 (Exception Flow)

- E1. [ADMIN이 아닌 사용자가 팀 정보 수정 또는 삭제 시도]: 시스템이 403 Forbidden을 반환한다.

## 5. 알림 관리 시나리오

### SC-N01 알림 목록 조회 및 읽음 처리

**관련 UC**: UC-N01, UC-N02
**액터**: 인증된 사용자
**사전 조건**: 사용자가 로그인 상태이며, 알림이 1건 이상 존재한다.
**사후 조건 (조회)**: 알림 목록이 최신순으로 표시되며, 읽지 않은 알림과 읽은 알림이 구분된다.
**사후 조건 (읽음 처리)**: 선택한 알림의 is_read 값이 true로 변경된다.

#### 기본 흐름 (Main Flow)

1. 사용자가 알림 아이콘 또는 알림 목록 페이지로 이동한다.
2. 시스템이 해당 사용자의 알림을 최신순으로 조회하여 표시한다.
3. 시스템이 읽지 않은 알림(is_read=false)을 시각적으로 강조하여 표시한다.
4. 사용자가 특정 알림을 클릭한다.
5. 시스템이 해당 알림의 is_read를 true로 변경한다.
6. 시스템이 알림 유형에 따라 해당 페이지로 이동한다 (예: TEAM_INVITE → 초대 상세, DUE_DATE_REMINDER → 할일 상세).

#### 대안 흐름 (Alternative Flow)

- A1. [전체 읽음 처리 버튼 클릭]: 시스템이 해당 사용자의 모든 알림을 is_read=true로 일괄 변경한다.
- A2. [DUE_DATE_REMINDER 알림 자동 발송]: 시스템이 마감일 1일 전(KST 기준) 해당 할일의 사용자에게 자동으로 알림을 발송한다. 해당 알림은 is_read=false로 생성된다.

#### 예외 흐름 (Exception Flow)

- E1. [알림이 없는 경우]: 시스템이 "알림이 없습니다" 안내 메시지를 표시한다.
- E2. [인증 토큰 없이 접근]: 시스템이 401 Unauthorized를 반환하고 로그인 페이지로 이동시킨다.
