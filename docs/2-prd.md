## 1. 프로젝트 개요

### 1.1 배경 및 목적

Todolist-App은 개인의 할일을 체계적으로 관리하고, 팀 멤버와 협업할 수 있도록 지원하는 **할일 관리 웹 애플리케이션**이다. 사용자는 할일을 생성·수정·삭제하고 카테고리 및 진행 상태로 분류하며, 팀 단위의 공유 환경에서 협업할 수 있다.

### 1.2 해결하는 문제

| REQ ID  | 문제                                                 | 해결 방향                                                     |
| ------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| REQ-001 | 개인별 할일을 체계적으로 관리할 수 있는 도구가 없다  | 할일 CRUD, 상태 관리, 카테고리 분류, 날짜 기반 보기 기능 제공 |
| REQ-002 | 팀 멤버와 할일을 공유하고 협업할 수 있는 도구가 없다 | 팀 생성, 멤버 초대, 팀별 권한 관리, 공유 할일 목록 기능 제공  |

### 1.3 목표 사용자

| 페르소나         | 설명                                | 주요 니즈                                    |
| ---------------- | ----------------------------------- | -------------------------------------------- |
| 개인 사용자      | 업무·일정을 관리하려는 직장인, 학생 | 나만의 할일 목록, 마감일 관리, 카테고리 분류 |
| 팀 리더          | 소규모 팀의 업무를 조율하는 관리자  | 팀원 초대, 권한 관리, 팀 할일 현황 파악      |
| 팀원             | 팀에 소속되어 할일을 수행하는 멤버  | 팀 할일 생성·수정, 진행 상태 업데이트        |
| 읽기 전용 구성원 | 할일 현황만 모니터링하는 이해관계자 | 팀 할일 조회                                 |

## 3. 기능 요구사항 상세

### 3.1 계정 관리

#### UC-A01 회원가입

- 이메일과 비밀번호로 계정 생성
- 비밀번호 정책: 최소 8자, 영문자·숫자·특수문자 각 1자 이상 포함 (USR-002-1)
- 중복 이메일 가입 불가 (USR-001)
- 가입 완료 시 기본 카테고리 자동 생성: 업무, 개인, 학습, 회의, 프로젝트, 긴급 업무 (CAT-003)

#### UC-A03 로그인

- 이메일/비밀번호 인증
- 성공 시 액세스 토큰(1시간)과 리프레시 토큰(7일) 발급 (AUTH-006)
- 만료·무효 토큰 요청 시 401 반환 후 재로그인 유도

#### UC-A07 / UC-A08 비밀번호 재설정

- 이메일로 재설정 링크 발송
- 링크 유효 시간: 발송 후 30분 (USR-005)
- 만료 링크 접근 시 재발송 안내

#### UC-A09 회원 탈퇴

- 소프트 삭제 아닌 **즉시 하드 삭제** 적용 (NFR 데이터 보존 정책)

### 3.2 할일 관리

#### UC-T01 할일 생성

- 필수 항목: 제목 (TODO-001)
- 선택 항목: 설명, 시작일, 종료일(마감일), 카테고리, 진행 상태
- 종료일은 시작일 이상이어야 함 (TODO-002)
- 진행 상태는 PLANNED, IN_PROGRESS, DONE, ON_HOLD 중 하나여야 함 (TODO-003)
- 진행 상태 기본값: PLANNED
- 개인 할일 생성 시 `user_id` 필수, `team_id`는 NULL (TODO-010)
- 팀 할일 생성 시 `team_id` 필수, `user_id`는 생성자 참조로 저장하되 nullable; ADMIN 또는 MEMBER 역할 필요 (AUTH-003, TODO-010)

#### UC-T02 할일 수정

- 사용자는 자신이 소유한 할일만 수정할 수 있다 (AUTH-002)
- 팀 할일 수정은 해당 팀의 ADMIN 또는 MEMBER 역할을 가진 사용자만 가능 (AUTH-003)
- 수정 가능 항목: 제목, 설명, 시작일, 종료일, 카테고리, 진행 상태
- 제목 필수, 종료일 ≥ 시작일 조건, 개인/팀 할일 소유 조건 유지 (TODO-001, TODO-002, TODO-010)

#### UC-T03 할일 삭제

- 사용자는 자신이 소유한 할일만 삭제할 수 있다 (AUTH-002)
- 팀 할일 삭제는 해당 팀의 ADMIN 또는 MEMBER 역할을 가진 사용자만 가능 (AUTH-003)
- 삭제 후 복구 불가 (하드 삭제) (TODO-004)

#### UC-T06 진행 상태 변경

- 허용된 상태 전이만 가능하며, 허용되지 않은 전이 시도 시 오류 반환 (TODO-008)
- DONE → IN_PROGRESS 전이는 재개(재작업) 상황에서 허용된다.

| 현재 \ 전환 | PLANNED | IN_PROGRESS | DONE | ON_HOLD |
| ----------- | ------- | ----------- | ---- | ------- |
| PLANNED     | -       | O           | X    | O       |
| IN_PROGRESS | X       | -           | O    | O       |
| DONE        | X       | O           | -    | X       |
| ON_HOLD     | O       | O           | X    | -       |

#### UC-T07 오늘 할일 조회

- `start_date ≤ 오늘 ≤ due_date` 조건 (TODO-005)
- 날짜 기준: KST (UTC+9) (TODO-009)

#### UC-T08 이번 주 할일 조회

- 현재 주 월요일~일요일 내에 `due_date`가 포함된 할일 (TODO-006)
- 날짜 기준: KST (UTC+9) (TODO-009)

#### UC-T09 / UC-T10 검색 및 필터

- 검색: 할일 제목 키워드 검색
- 필터: 진행 상태, 카테고리, 마감일 범위
- 기본 정렬: `due_date` 오름차순 (TODO-007)

### 3.3 카테고리 관리

- 카테고리는 **사용자(USER)** 또는 **팀(TEAM)** 중 하나를 소유 주체(`owner_type`)로 가진다.
  - 사용자 카테고리: 해당 사용자의 개인 할일 분류에 사용
  - 팀 카테고리: 해당 팀의 팀 할일 분류에 사용; 팀 ADMIN만 생성·수정·삭제 가능
- 카테고리명은 동일 소유자(사용자 또는 팀) 내 중복 불가 (CAT-001)
- 색상 태그는 HEX 코드 형식 (#RRGGBB) 저장 (CAT-004)
- 카테고리 삭제 시 해당 카테고리에 속한 할일의 `category_id`는 NULL 처리 (CAT-002)

### 3.4 팀 관리

**팀 규칙**

- 팀 생성자는 자동으로 ADMIN 역할 부여 (TEAM-001)
- 팀에 최소 1명의 ADMIN 상시 유지; 마지막 ADMIN은 역할 변경·탈퇴 불가 (TEAM-002)
- 동일 팀 중복 가입 불가 (TEAM-003)
- 탈퇴 시 해당 사용자가 생성한 팀 할일 소유권은 `team_id` 기준으로 팀에 귀속되며, 해당 할일의 `user_id`는 NULL 처리 가능 (TEAM-004, TODO-010)
- 팀 삭제 시 팀의 모든 할일·카테고리 함께 삭제; 멤버 개인 할일 영향 없음 (TEAM-005)

**역할별 권한**

| 기능 | ADMIN | MEMBER | VIEWER |
|------|-------|--------|--------|
| 팀 할일 조회 | ✅ | ✅ | ✅ |
| 팀 할일 생성·수정·삭제 | ✅ | ✅ | ❌ (AUTH-004) |
| 팀 카테고리 생성·수정·삭제 | ✅ | ❌ | ❌ |
| 팀 멤버 초대 | ✅ | ❌ | ❌ (AUTH-005) |
| 팀 멤버 역할 변경 | ✅ | ❌ | ❌ (AUTH-005) |
| 팀 멤버 추방 | ✅ | ❌ | ❌ (AUTH-005) |
| 팀 정보 수정 | ✅ | ❌ | ❌ |
| 팀 삭제 | ✅ | ❌ | ❌ |

**팀 초대 모델**

- 팀 초대는 `TeamInvitation`으로 관리한다.
- 주요 필드: `invitation_id`, `team_id`, `invited_user_id`, `invited_by`, `role`, `status`, `expires_at`, `created_at`, `responded_at`.
- `status`는 PENDING, ACCEPTED, DECLINED, EXPIRED 중 하나이다.

**UC-M02 팀 멤버 초대**

- ADMIN은 기존 사용자에게 MEMBER 또는 VIEWER 역할로 팀 초대를 생성할 수 있다 (INV-001).
- 이미 팀에 소속된 사용자 또는 동일 팀에 PENDING 초대가 있는 사용자는 초대할 수 없다 (TEAM-003, INV-002).
- 초대 생성 시 `TEAM_INVITE` 인앱 알림을 발송한다 (NOTIF-002).

**UC-M09 팀 초대 수락**

- 피초대자가 PENDING 초대를 수락하면 `TeamInvitation.status=ACCEPTED`로 변경하고 TeamMember를 생성한다 (INV-003).
- 부여 역할은 초대의 `role` 값을 따른다.
- 이미 팀에 소속된 사용자는 수락 불가 (TEAM-003)
- 만료된 초대는 수락할 수 없으며 EXPIRED로 처리한다 (INV-005).
- 수락 시 관련 `TEAM_INVITE` 알림 상태를 읽음 처리한다.

**UC-M10 팀 초대 거절**

- 피초대자가 초대를 거절하면 `TeamInvitation.status=DECLINED`로 변경하며 팀에 가입되지 않는다 (INV-004).
- 거절 후 동일 팀에 재초대 가능

### 3.5 알림 관리

**채널 구분**

| 채널 | 용도 |
|------|------|
| 인앱 알림 | DUE_DATE_REMINDER, TEAM_INVITE, TODO_ASSIGNED 등 앱 내 이벤트 알림 |
| 이메일 | 비밀번호 재설정 링크 발송 전용 (알림 시스템과 별개, 외부 이메일 서비스 연동) |

**인앱 알림 유형**

- `DUE_DATE_REMINDER`: 할일 마감일 1일 전 자동 발송 (NOTIF-001)
- `TEAM_INVITE`: 팀 초대 발생 시 피초대자에게 발송하며 관련 `invitation_id`를 참조 (NOTIF-002)
- `TODO_ASSIGNED`: 팀 할일 배정 시 발송

**알림 상태 관리**

- 읽지 않은 알림은 `is_read=false`로 관리; 사용자가 확인 시 `true`로 변경 (NOTIF-003)
- 알림 목록은 최신순 정렬

## 4. 비기능적 요구사항 (NFR)

### 4.1 성능

| 항목           | 목표                                      |
| -------------- | ----------------------------------------- |
| 동시 접속자 수 | 500 CCU                                   |
| API 응답 시간  | 일반 조회 요청 95th percentile ≤ 500ms    |
| DB 커넥션 풀   | CCU에 맞게 PostgreSQL 커넥션 풀 적정 설정 |

### 4.2 보안

| 항목          | 요구사항                                        |
| ------------- | ----------------------------------------------- |
| 전송 보안     | HTTPS 필수 (HTTP 접근 시 HTTPS 리다이렉트)      |
| 인증          | JWT 기반; 액세스 토큰 1시간 / 리프레시 토큰 7일 |
| 비밀번호      | bcrypt 해싱 저장; 평문 저장 금지                |
| API 접근 제어 | 인증된 사용자만 내 정보, 할일, 카테고리, 팀, 알림 API 접근 가능 |
| 향후 확장     | OAuth2 소셜 로그인 (2차)                        |

### 4.3 데이터 보존 정책

| 항목      | 정책                                    |
| --------- | --------------------------------------- |
| 회원 탈퇴 | 탈퇴 즉시 사용자 데이터 하드 삭제       |
| 할일 삭제 | 하드 삭제 (복구 불가) (TODO-004)        |
| 팀 삭제   | 팀 및 팀의 모든 할일·카테고리 즉시 삭제 |

### 4.4 감사 로그 (Audit Log)

- 아래 대상 엔티티의 **생성·수정·삭제** 이벤트에 대해 변경 이력을 저장한다.
- 저장 항목: 대상 엔티티, 엔티티 ID, 변경 유형(CREATE/UPDATE/DELETE), 변경자 user_id(nullable), 변경 일시, 변경 전·후 값(JSON), 메타데이터(JSON)
- 사용자 하드 삭제가 감사 로그 보존을 막지 않도록 `actor_user_id`는 nullable로 관리한다.
- 비밀번호 해시, 인증 토큰, 비밀번호 재설정 링크 등 민감 정보는 감사 로그에 저장하지 않는다.
- User 삭제 이벤트는 이메일·이름 등 개인정보를 마스킹하거나 제외한다.

## 6. API 설계 원칙

- REST API 설계 준수 (HTTP 메서드 의미에 맞게 사용)
- 응답 포맷: JSON
- 인증 헤더: `Authorization: Bearer <access_token>`
- 에러 응답 포맷 통일:
  ```json
  {
    "code": "ERROR_CODE",
    "message": "오류 설명"
  }
  ```
- HTTP 상태 코드 기준:
  - `200 OK`: 조회/수정 성공
  - `201 Created`: 생성 성공
  - `204 No Content`: 삭제 성공
  - `400 Bad Request`: 입력값 오류
  - `401 Unauthorized`: 인증 실패 / 토큰 만료
  - `403 Forbidden`: 권한 없음
  - `404 Not Found`: 리소스 없음
  - `409 Conflict`: 중복 데이터 (이메일, 카테고리명 등)
  - `422 Unprocessable Entity`: 비즈니스 규칙 위반 (상태 전이 오류 등)
